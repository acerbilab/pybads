# Fix report: W2-45 (integer-typed bounds, slice B1)

## W2-45: `ea446ec` fix: integer-typed bounds and x0 are taken as floats, so that the log transform of a bound is not truncated (W2-45)

**Files changed:** `pybads/bads/bads.py` (`_bounds_check_`, +19 lines) and `pybads/testing/bads/test_bads_inputs.py` (+36 lines, one new test). Worktree `/home/user/pybads-fix-F`, branch `w2-fix-F`, parent `17d265e`.

**What changed and why.**
- **The defect.** `VariableTransformer` copies the bounds, then writes the log of a log-scaled variable's bounds into those copies in place. An integer-typed array therefore gets truncated logs. Since W2-3 a scalar bound is broadcast with its own dtype, so an integer scalar at D > 1 hit this too.
- **The fix.** `_bounds_check_` now converts `x0` and the four bounds with `np.asarray(..., dtype=float)`, so every step after that point works on floats: the remaining checks, the call of `non_box_cons` on the plausible bounds, `VariableTransformer`, the random start and the grid.
- **Where the cast sits.** I put it right after the real-valued test, not at the very top as "before anything else reads them" would have it:
  - A cast before that test would turn a complex `x0` with a nonzero imaginary part into a float (with only a NumPy `ComplexWarning`), so the check could no longer refuse it. Casting after the test keeps all the checks as they were; I checked that a complex `x0` is still refused.
  - The checks that run before the cast (shapes, a single starting point, finite plausible bounds, real values) give the same answer for integers and floats.
- **Floats and shapes.** A float64 input comes back from `np.asarray` as the same object, so float runs are unchanged. Shapes are unchanged.
- The commit body explains all this, with the numbers from `int_bounds_fef6c14.out`.

**Does the setup write into the user's arrays?** I checked with `scratchpad/fix/F/writethrough.py`: 1-D and 2-D, float and integer arrays, with and without plausible bounds, a log-scaled and a linear variable, and a 30-evaluation `optimize()`.
- **Before the fix:** none. The user's arrays are unchanged after `BADS(...)` and after `optimize()`.
  - `__init__` copies `x0`, and also the hard bounds when it uses them as the missing plausible bounds.
  - `_bounds_check_` returns the bounds as the user's own arrays or views of them. Nothing writes into them before `_init_optim_state_` replaces `self.lower_bounds` and the others with copies from `VariableTransformer`.
  - `VariableTransformer` copies its inputs before its in-place log.
  - After construction, no `BADS` attribute shares memory with a user array.
- **After the fix:** the same for float arrays. Integer arrays are now copied by the cast, so they are not aliased at all.
- This is safe, but it holds only because no step writes into the bounds while `_bounds_check_`'s outputs alias them.

**Test:** `pybads/testing/bads/test_bads_inputs.py::test_integer_bounds_are_taken_as_floats`, 4 cases:
- `arrays`: a log-scaled variable beside a linear one, D = 2;
- `arrays_plausible_omitted`: the same without plausible bounds;

- `scalars_linear`: scalars -10, 10, -5, 5 at D = 2.

Each case uses an integer `x0` and compares a `BADS` built from integers with one built from the same values as floats. It checks the log flags, then that `x0`, `lb`/`ub`/`plb`/`pub` in u, the four `*_orig` bounds and `optim_state["u"]` (the start on the grid) are equal, then that all of them are float arrays. Construction only, no `optimize()`.

**Proposed changelog line (Fixed):**
- **Integer bounds.** Bounds and `x0` given as integers, as an integer array or an integer scalar such as `lower_bounds=1`, are taken as the same values as floats, as in MATLAB BADS. With integer bounds on a variable that BADS log-transforms, 1.1.0 truncated the logs of the bounds, so the plausible box and the hard bounds were mapped to the wrong range. Results change on such problems.

**Upgrading from:** I don't think it needs a new line; the existing "Results differ from 1.1.0, also with a fixed seed" covers the changed runs. The only other visible difference is that `result["x0"]` (and `bads.x0`) is now a float array for an integer `x0`. If you want that spelled out: "`x0` and the bounds given as integers are converted to floats: the result's `x0` is a float array."

**Uncertain:** placing the cast after the real-valued test rather than first is my choice, for the reason above. It is also why a complex input with a zero imaginary part now changes (last item below).

## Noticed outside my row
- **`VariableTransformer` used directly.** It is public (documented in `docsrc/source/api/classes/parameter_transformer.rst`) and still truncates when given integer arrays, since the cast is only in `BADS`. Casting its own copies (`lb = lower_bounds.copy()` and the three siblings) to float would cover direct users too.
- **float32 inputs** now become float64. Before, they stayed float32 all the way through the transform, including the in-place log. I think that is harmless, and probably better.
- **A complex `x0` or bound with a zero imaginary part** passes the real-valued test (`np.isreal` is elementwise). Before, it was carried through as complex128 (`bads.x0` was complex); now it becomes float64 with a NumPy `ComplexWarning`. MATLAB's `isreal` is false for an array stored as complex even with zero imaginary parts. This is a minor point.
- Between `fef6c14` and the current base, the float run of `int_bounds.py` changed (x `[9.9991, 10.0026]` → `[9.9984, 10.0002]`). That comes from the other fixes of the pass (W2-4 and the others), not from this row.
