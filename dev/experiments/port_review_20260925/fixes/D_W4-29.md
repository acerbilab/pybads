## W4-29: `f906ba4` fix: refuse a hedge_beta that is not a finite number at least 0 and a hedge_decay outside [0, 1] when BADS is created (W4-29)

**What changed**
- **Both checks follow W4-18's form.** Each is a `try` block that refuses a bool first, then tests `bool(<comparison>)` and catches `TypeError`/`ValueError`. So a bool, a string, a Python complex, NaN and an array of several values are refused.
- **`hedge_beta`** must satisfy `0 <= hedge_beta < np.inf`. 0 stays accepted (a uniform choice).
  - Message: `options['hedge_beta'] needs to be a finite number greater than or equal to 0, not -1.0; its default is 1e-3 / options['tol_fun'].`
- **`hedge_decay`** must satisfy `0 <= hedge_decay <= 1`, so 0 and 1 are accepted.
  - Message: `options['hedge_decay'] needs to lie between 0 and 1, not ….`
- **Comments.** Each check has a short comment saying what goes wrong outside the range, and cites the MATLAB line that uses the option unchecked: `searchHedge.m:45` for the softmax, `acqPortfolio.m:69` for the decay update. `bads.m:289-290` (the defaults) is cited in the commit body.
- **`.ini` descriptions** (one line each):
  - `hedge_beta`: "…from the searches' gains, finite and at least 0 (0 is a uniform choice)"
  - `hedge_decay`: "…at each update, from 0 to 1 (1 is no decay)"
- **The defaults pass at every D.** `hedge_beta` is 1 at the default `tol_fun`. `hedge_decay = 0.1**(1/(2*D))` lies in [0.316, 1).

**Proposed changelog lines** (relative to 1.1.0; I did not edit `CHANGELOG.md`):
- Upgrading from: "`BADS` raises `ValueError` for a `hedge_beta` that is not a finite number at least 0, which the default `1e-3 / tol_fun` is when `tol_fun` is negative, and for a `hedge_decay` outside [0, 1]."

**Uncertain**
- **NumPy complex scalars get through.** W4-18's form, which I kept, refuses a Python `complex` with a `TypeError`. But NumPy 2.4.6 orders complex numbers lexicographically, so `np.complex128(0.5)` passes the comparison and is accepted. The same holds for the existing checks of `hedge_gamma` and `improvement_quantile`. I kept the form rather than add a stricter check to these two alone.
- **One-element and 0-d arrays are accepted and stored as arrays**, as W4-18's check does for `hedge_gamma`.

## Outside the row (not changed)
- **`tol_fun` itself is never checked.**
  - `tol_fun=0` or `0.0` raises a bare `ZeroDivisionError` while the `.ini` default `1e-3/self.get('tol_fun')` is evaluated, before any check runs.
  - `np.float64(0.0)` gives `hedge_beta = inf` with a RuntimeWarning; this is now refused, with the message naming `tol_fun`.
  - A negative `tol_fun` is refused only through `hedge_beta`, so a user who also sets `hedge_beta` still runs with a negative `tol_fun`.
