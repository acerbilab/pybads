## W2-46: `356235d` fix: no overflow warning from the masked exponential of a linear variable beside a log-scaled one (W2-46)

- **Files:**
  - `pybads/variable_transformer/variables_transformer.py`
  - `pybads/testing/variable_transformer/test_variable_transformer.py` (adds `import warnings` and the test)
- **What changed:**
  - In the branch that mixes log-scaled and linear variables, the `ginv` lambda is now a nested `def ginv(y)`, with a one-line comment. It computes `np.minimum(finfo.max, np.exp(gamma * y + mu))` under `np.errstate(over="ignore")` and returns the same masked sum as before, so every value is the same.
  - This is the smallest scope that covers every case, because the warning also came during runs, not only at construction. A run with a linear variable at 800 beside a log-scaled one printed the warning in `BADS(...)` and again in `optimize()`. After the fix it prints none, and `x` and `fval` are identical (`runtime46_before.out` / `runtime46_after.out`).
  - MATLAB's `transvars.m:157-158` computes the same `min(realmax, exp(...))`. MATLAB gives Inf silently where NumPy warns.

  - `ub = inf`, which the self-test takes at 1e6;
  - `ub = 1e300`;
  - `lb = 1e-300`.

  None warns before or after (`repro46_*.out`). Every column in that branch is log-scaled, so no exponential is masked out, and a lower bound is always positive. It can overflow only for a point beyond the largest float in the original space. That overflow is real and is clamped at `finfo.max`; I left it unchanged, and it still warns.

## W2-47: `78a7dd6` fix: VariableTransformer takes float copies of the bounds, so that integer bounds given to it directly are not truncated (W2-47)

- **Files:**
  - `pybads/variable_transformer/variables_transformer.py`
  - `pybads/testing/variable_transformer/test_variable_transformer.py`
- **What changed:**
  - The six `.copy()` calls that produce `lb`, `ub`, `plb` and `pub` are now `.astype(float)`, which also copies. A comment says why. Two of the six are in `plb`/`pub` branches that can never run.
  - The plausible bounds that default to the hard ones (`np.copy(lower_bounds)`) now go through the `plb`/`pub` cast, so those lines are unchanged.
  - I chose `.astype(float)` over the brief's `np.array(..., dtype=float)`: `np.array` turns a NumPy scalar into a 0-d array. The `np.isscalar` broadcast that follows would then skip it, which breaks NumPy scalar bounds, which work today. With `.astype(float)`, the inputs accepted are exactly those `.copy()` accepted, and shapes are kept.
  - float64 input gives identical values and shapes; float32 input now becomes float64 (`repro47_before.out` / `repro47_after.out`).
- **Test:** `test_integer_bounds_are_taken_as_floats[plausible|plausible_omitted]`.
  - Setup: integer arrays `lb = [1, -10]`, `ub = [1000, 10]`, with plausible bounds `[2, -5]` / `[500, 5]` or with them omitted.
  - It compares against the same values as floats: log flags `[True, False]`, the transformed and `orig_*` bounds, the transform of two points and the inverse, then checks that the bounds are float.
  - Parent: `2 failed, 21 deselected`:
    - `[0, 0]: -1.0 (ACTUAL), -1.2510738338534912 (DESIRED)` (lb in u, plausible bounds given);
    - `[0, 0]: 1.3025850929940457 (ACTUAL), 1.0 (DESIRED)` (ub in u, plausible bounds omitted).
  - Commit: `2 passed`; the whole file gives `23 passed`. W2-45's `test_bads_inputs.py -k integer` still passes (4 passed).
- **Fingerprint:** `dc11118754b18b47`.
- **Proposed changelog wording:** add a sentence to the unreleased "Integer bounds" entry.
  - "…The same holds for `VariableTransformer` used directly, whose bounds are now float copies (a float32 bound becomes float64)."
  - Upgrading from: none. It only changes wrong results, and the `orig_*` attributes of an integer input are now float arrays.

## Noticed outside my rows (not fixed)

- **Scalar `apply_log_t` fails.** `VariableTransformer(..., apply_log_t=False)` raises `AttributeError: 'VariableTransformer' object has no attribute 'apply_log_t'`, because the scalar branch reads `self.apply_log_t` before assigning it (it should read the argument). BADS always passes `None` or an array, so only direct use meets it.
- **Inputs a direct user can meet:**
  - A 1-D bound array raises `IndexError`; (1, D) arrays are required, but the docstring does not say so.
  - A NumPy scalar hard bound with the plausible bounds omitted fails, because `np.copy` of a scalar gives a 0-d array that is not broadcast.
- **Dead branches.** In `__init__`, the `else` branches of the `lb`/`ub`/`plb`/`pub` expressions can never run, because the defaults are set just above them.
- **Docstring wording.** The class docstring says the log transform applies when the variables "span more than one order of magnitude". The code tests `pub/plb >= 10`, so it applies at exactly one order too.
